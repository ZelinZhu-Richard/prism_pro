# Ordinary-folder identity foundation — 2026-11-02

This is an internal backend foundation for in-place folder opening. **The user-facing Open File/Open Folder workflow is not delivered yet.** No new path-opening API or browser control is exposed in this increment. Bounded inventory/approval, folder recovery UI and safe linked-folder batch operations remain required before launch. Uploading/copying a folder is not a substitute for the approved in-place requirement.

## Implemented boundary

`ProjectDirectories` records an explicitly captured canonical folder path, device, inode and birth identity separately from document source/history. Existing managed projects retain their old storage shape and locations. A linked project uses the chosen ordinary directory for physical file access; its metadata/history stays in Leaf's application data.

Adoption indexes matching existing source bytes without rewriting files, changing their permissions/modification timestamps or renaming the chosen root. Candidates cannot overlap Leaf data or another available linked project. Path-component comparison includes filesystem roots and normalized spelling, without treating a shared text prefix as a directory boundary. Explicit protected/parent/control/invalid-Unicode paths fail before filesystem lookup; final-component symlink roots and unsafe indexed descendants are refused.

Every linked source-directory resolution revalidates its recorded identity. Missing, moved, replaced, symlinked, unreadable or corrupt bindings fail closed. Startup does not recreate the folder or fall back to a managed source directory. Other projects remain usable. An explicit moved-folder relink requires the original identity, the reviewed source generation and no competing agent owner; it does not silently adopt a replacement folder.

Source saves retain existing atomic write receipts, revision conflicts and recoverable versions. A destination that is read-only at preflight is rejected before a changed source commits or an unnecessary write receipt is created. A filesystem failure after a source commit is retained as a per-project recovery problem instead of crashing startup for all projects. Staging rechecks the bound root, so a replacement folder cannot receive the intended original-folder write merely because its file happens to have the old content hash.

Linked project Trash is metadata-only. Restoring it reconciles external changes before any source write; an unavailable folder stays unavailable and is never recreated. Source ZIPs, independent managed copies, source checkpoints and AI context use indexed relative files; directory binding, hidden configuration and unindexed content do not become source exports or automatic provider context.

## Whole-tree operations remain pending

The current managed move/upload/batch implementation copies and swaps a source tree under a parent with literal `files` recovery paths. That mechanism must not rename or recover a user's ordinary folder or inspect a sibling journal. Linked roots are therefore blocked at these legacy mutation boundaries before source/receipt/history changes. This is a temporary internal guard while the folder workflow is being built, not a delivered limitation accepted as final success. Ordinary managed-project operations remain available and pass the full suite.

The next implementation must adapt move/rename, uploads, file/folder Trash/restore and Undo to preserve unknown entries and root identity, including crash recovery. Reviewed path selection/inventory, existing-folder lookup/relink, main-document selection and read-only/unavailable-folder UI must then join the existing guarded navigation/recovery flows. The complete Leaf goal remains active.
